# Developing Map Studio

How to build the module, run the local development Gateway and run the tests. For what Map Studio does and how to install it, see the [README](../README.md).

## Kept from the spike

Kept from the spike until later epics replace them: clicking a point sends `point.click` and the Gateway answers `point.click.reply` with the time it received the click (the echo shows in the component's status line in Edit mode alone since epic 3 entry 15; in View mode the line shows only a save status, a failed load, a read-only store or unsaved edits); a "Draw a line" toggle (top right, under the zoom card) starts Terra Draw's line tool (click to add points, Enter to finish, Escape to cancel), and the finished line is saved to the map store; since epic 3 entry 14 it belongs to Edit mode alone, shown only where the `editMode` prop is true (the dev editing page `/edit`; [docs/contract.md](contract.md), "The component's props"), so View mode never shows it and the e2e specs that draw lines open `/edit`; the spike's `popupView` prop is retired (epic 3 entry 8): a point's popup comes from its kind setup, the default popup or the setup's `popupView` ([docs/contract.md](contract.md), "The popup"). Story 7's spike-only prop `testSet` is gone (epic 2 story 11): the dev map's 30-pad set and the tracer's points are map items seeded through `system.mapstudio.applyEdits` (the `/edit` page's "Seed the dev map", MapEditor only, safe to re-run; since epic 3 entry 15 the same press seeds the showcase map too).

## Build

Requirements: JDK 17 and Docker. Node 22 is downloaded by the build; nothing else needs installing. Running `npm` in `web/` outside Gradle needs Node 20.9 or later (the webpack plugins' floor).

```bash
./gradlew build                      # produces build/Map-Studio.unsigned.modl
cd web && npx tsc --noEmit && npm test   # type check and the Jest unit tests alone
```

The build fails when the web bundle does not compile or a unit test fails. The bundle is `MapStudio.js` and `MapStudio.css`, served at `/res/mapstudio/`, with MapLibre's worker beside them as `maplibre-gl-worker.js` (MapLibre 6 runs its worker from a separate file; the component points it there). Signing happens only when `-Pignition.signing.*` properties are passed (release jobs); a plain build stays unsigned.

Layout:

| Folder | What lives there |
| --- | --- |
| `common/` | component descriptor, props schema (`mapstudio.props.json`), the message contract (`Messages.java`) |
| `gateway/` | gateway hook and the component model delegate (`MapStudioDelegate`); `system.mapstudio` script functions are declared and documented in `common/` (`MapStudioScriptModule` and its `.properties`: `getMap`, `applyEdits`, `refreshAdapters`, `ping`) and run in `gateway/.../script/` |
| `designer/` | the Designer palette entry |
| `web/` | the TypeScript and React component, MapLibre map, Terra Draw line tool (`DrawControl.tsx`, `draw.ts`), message client (`messages.ts`), the point popup (`DefaultPopup.tsx`, `PointPopup.tsx`, `popupParams.ts`) and their tests |
| `e2e/` | the Playwright suite (pinned `@playwright/test`): smoke tests at 1440 and 390 px, the popup checks and the spike's measures |
| `ops/` | the local development Gateway (Docker) and its `mapstudio-dev` project (`MapStudioDev` at `/`, `MapStudioEdit` at `/edit` with the script checks and the seed button, `MapStudioAdapters`, `MapStudioLive` at `/live`, the alarm page `MapStudioAlarms` at `/alarms/:item` and the pad page `MapStudioPad` at `/pad/:name` (where the popup's View alarms and page link land), the example custom popup view `Popups/PadAlarms`; project libraries `mapstudio_dev`, the dev kind and asset adapter and the dev views' role check, and `mapstudio_seed`, the dev seed) |
| `docs/` | contributor architecture, the platform checks and screenshots |

## The showcase project

`ops/showcase/project` is a second bind-mounted project, `mapstudio-showcase` (epic 3 entry 15): one page, `/`, with the Map Studio component alone, no test control or readout, opened at zoom 15 on a Mesa-like demo field with the UX mockups' names, kinds, places and states (`_bmad-output/initiative-flowmap/ux-map-studio/mockups/`): P14 in a priority 1 unacknowledged alarm "Casing pressure high - P14-2H" (1,240 psi casing, 410 psi tubing, 1.8 MMcf/d), P21 comms lost, SWD1 stale, CTB1, CS01, P12, the pipeline L-SWD from CTB1 to SWD1 with PT-1, LV-1 and PT-2 on it, the pipeline L-GL21, two laterals and the Mesa lease geofence. Its kinds and assets come from its own project library `mapstudio_showcase`; its tags are the dev tag provider's `Showcase` folder (`ops/config/core`, so a stack from before the entry needs `ops/up.sh --fresh` once); its map items, kind setups and the demo tags' states are seeded by the dev project's `/edit` page, **Seed the dev map**, which seeds both maps (project library `mapstudio_showcase_seed`, its result under `showcase`; MapEditor only, safe to re-run; run it again after a Gateway restart, which keeps the memory tags' values but not SWD1's stale quality). The basemap is None (the theme's blank background, so the renders need no tiles); the Legend panel offers OpenStreetMap too. Session: http://localhost:9088/data/perspective/client/mapstudio-showcase. The places are the mockups' pixel places at zoom 15 round the starting area, so the field is compact (L-SWD is about 0.45 km; the mockups' "2.9 km" was not drawn to scale).

Entry 12 (the engineering review pack, [review-er27.md](review-er27.md)) adds to the showcase project: the page `/dark` (view `ShowcaseDark`, the component alone again, whose view startup script sets the session's theme to dark so the pack renders both themes; a session keeps the theme, a new one starts light), the custom popup view `Popups/SiteCard` that the SWD kind setup names as its `popupView` (SWD1's popup is the project view under Map Studio's own close row), and review alarm tags in the `Showcase` folder (`CS01/CS01-K1` Medium, `CTB1/CTB1-T3` Low, `P12/P12-1H` High, `PT1/PT1-A` Medium, `PT2/PT2-A` Low, dev-only test equipment, quiet after the seed). The dev `/live` page's buttons **Showcase review alarms**, **Showcase review stale** and **Showcase review off** (`mapstudio_showcase_seed.review_states`) raise them (P12's and PT-2's acknowledged), add PT-2 comms lost, and put the mockups' states back; `e2e/tests/review.spec.mjs` renders the review states in both themes (`docs/screenshots/review-<theme>-*.png`) and runs the contrast check of every hue token (`e2e/lib/contrast.mjs`; the tables `docs/review-er27-contrast-<theme>.md`).

`e2e/tests/showcase.spec.mjs` seeds it and renders the same five views as the mockups; with `E2E_DOCS=1` they are the committed `docs/screenshots/showcase-*.png`: [view mode at 1440 px](screenshots/showcase-view-mode-1440.png), [the Needs you list and the legend open](screenshots/showcase-view-mode-needs-you-1440.png), [P14's popup at 1366 px](screenshots/showcase-view-desktop-popup-1366.png), [the L-SWD line popup at zoom 16](screenshots/showcase-line-instruments-1366.png) and [P14's bottom sheet at 390 px](screenshots/showcase-phone-sheet-390.png). `node scripts/showcase-compare.mjs` composes each beside its mockup into `docs/screenshots/showcase-compare-*.png` (Playwright from `e2e/node_modules`, no other dependency) for the UX comparison `_bmad-output/initiative-flowmap/ux-map-studio/review-showcase-vs-mockups.md`.

## Run the development Gateway

```bash
ops/up.sh              # build, stage the .modl, start Ignition 8.3.10 in Docker, accept the module unattended
ops/logs.sh -n 200     # Gateway log
ops/down.sh [--purge]  # stop; --purge also wipes the Gateway and PostgreSQL data
ops/psql.sh            # psql on the dev map store (for example: ops/psql.sh -c "select * from mapstudio_edit")
ops/store-checks.sh    # map store checks: missing rights, a failed migration, the retry, a newer schema (operations.md)
```

The dev stack also runs **PostgreSQL 16**, the map store: no host port, reached by the Gateway as `postgres`. Its password is generated into the git-ignored `ops/secrets/` (by `ops/gen_secrets.py`) and reaches the Gateway's `MapStudio` database connection only through the `MapStudioFiles` File secret provider (`ops/config/core`, copied into the Gateway's `core` collection on a fresh volume). `ops/up.sh` also makes a dev API key (git-ignored, allowed in the Gateway's security properties by `ops/dev_security.py`) and uses it to make sure the identity provider `default` the dev project signs in with exists, then to create the **map editor** user `mapeditor` with the role `MapEditor` and the **phone editor** user `mapoperator` with the role `MapOperator` (`ops/users.py`); their passwords are `MAPSTUDIO_EDITOR_PASSWORD` and `MAPSTUDIO_OPERATOR_PASSWORD` in `.env`. The dev project's `/edit` page has a Log in button and a "Run script checks" button that calls `system.mapstudio` only for a signed-in user holding `MapEditor`; the anonymous session is a viewer. The e2e suite signs the editor (and the phone editor) in before each test that needs them in a separate process, outside the test runner, so no trace or report holds a password, and its teardown checks `e2e/out` for both. If you delete `ops/secrets/` while the PostgreSQL volume still exists, `ops/up.sh` refuses and asks for `--fresh` (the volume keeps the old password). The contract the map store follows is in [docs/contract.md](contract.md). The dev project's kind and asset lists come from its project library `mapstudio_dev`, whose `/adapters` page switches it between good, empty, broken, slow and incomplete lists (map editors only); the contract for those functions is in [docs/kinds-and-assets.md](kinds-and-assets.md). The dev project's Map Studio setup is `ops/project/com.aoindustrial.perspective.mapstudio/setup/setup.json` ([docs/setup.md](setup.md)); after editing it, `ops/scan.sh` has the Gateway read the project again, with no restart.

Each checkout has its own compose project, containers and volumes, named by `MAPSTUDIO_CONTAINER` in its `.env`; when you do not set one, the first `ops/` script derives `ms-<8 hex digits of the checkout path's SHA-256>` and records it there, so `--fresh` or `--purge` in one checkout never removes another checkout's Gateway or PostgreSQL. (Before this, an unset `MAPSTUDIO_CONTAINER` meant the shared compose project `ops`; remove its leftovers yourself with `docker compose -p ops -f ops/docker-compose.yml down -v` once nothing uses them.) To run several dev Gateways side by side, also give each its own `GATEWAY_HTTP_PORT`. The Gateway is at http://localhost:9088 (user `admin`, with a random password generated into the git-ignored `.env` on first start; development only, bound to localhost) and the session at http://localhost:9088/data/perspective/client/mapstudio-dev. The `mapstudio-dev` project is bind-mounted from `ops/project`, so Designer saves write back into the repository. For that the Gateway runs as you: the first `ops/` script records your uid and gid as `IGNITION_UID` and `IGNITION_GID` in `.env`, the Gateway container starts as root and the image's entrypoint remaps its `ignition` user to those ids and steps down to them with `gosu` (the image's own `IGNITION_UID` / `IGNITION_GID` support), so the files it writes into `ops/project` are yours, with your usual mode, and nothing in the repository is made world-writable. The ids must be your own: on each container creation the entrypoint re-owns whatever under its install folder is not `IGNITION_UID:IGNITION_GID`, the bind-mounted `ops/project` and `ops/store-checks/project` included, so with your own ids nothing in the repository changes, and with someone else's ids those folders would become theirs. Before this the Gateway ran as the image's user 2003 and every Designer save failed with `PushException: I/O error during prepare ... .tmp`. An existing checkout needs no `--fresh`: `ops/up.sh` recreates a Gateway container that predates the mapping and the entrypoint re-owns the kept data volume on its first start (one "Adjusting ownership of N Ignition installation files" line; it re-owns the whole install, which took 2.5 minutes on a slow disk and happens on every container creation, `--fresh` or a `down` and `up`, not on a restart). If you ever run the scripts as a different user, delete the two lines from `.env` so they are recorded again. The Gateway reads project files at start-up and at a project scan: after editing them by hand, run `ops/scan.sh` (no restart needed).

The dev Gateway loads the unsigned build (`-Dignition.allowunsignedmodules=true`), which is never acceptable outside development. Releases are signed `.modl` files on GitHub.

### Platform checks

The spike's Gateway questions (Alarm Metrics subscription, a project script called from module code, `system.mapstudio` functions, a custom project resource, PostgreSQL rights) were answered by a spike package and `ops/checks.sh`, which the refactor sweep removed. Results and evidence are in [docs/platform-checks.md](platform-checks.md); the harness itself is in the history at commit `51104c8`. If you ran it on your machine, its leftovers are yours to remove: the PostgreSQL volume (`docker volume ls`, then `docker volume rm <project>_postgres-data`) and the git-ignored `ops/checks/secrets/` folder. The checks also seeded config into the dev Gateway's own data volume (the Checks tag provider and UDT, with the dev-only test alarm `Checks/Pump Toggled` that toggles every 30 s, two database connections and a File secret provider); that config outlives the deleted files, so wipe it with `ops/down.sh --purge` or start once with `ops/up.sh --fresh`.

## Tests and proof

The Playwright suite in `e2e/` runs against a dev Gateway that is already up (`ops/up.sh`); CI starts one in Docker for every push to `main` and every pull request.

```bash
cd e2e && npm ci
npm test               # smoke tests, popup checks and measures; output in e2e/out (screenshots, measures.json, HTML report)
npm run docs           # the same, rewriting docs/screenshots/*.png and docs/spike-measures.json
npm run test:unit      # the suite's own helper tests (no Gateway needed)
```

The Gateway URL is `GATEWAY_URL`, else `http://localhost:` and `GATEWAY_HTTP_PORT` from `.env`, else 9088. The suite fails on any browser console or page error. It uses Playwright's own Chromium: on a laptop run `npx playwright install chromium` once in `e2e/` before the first run (on Ubuntu possibly `sudo npx playwright install-deps chromium` as well; CI does both). Set `PW_CHROMIUM_PATH` to use a browser already on the machine, and `E2E_HEADED=1` to run with a visible browser. A headed run is not by itself a GPU run: Playwright's Chromium under WSL (WSLg) reported SwiftShader (software WebGL) with every frame at 33.3 ms (a 30 Hz-like cadence). A frame-rate reading needs a browser whose `chrome://gpu` shows hardware-accelerated WebGL; under WSL use the Windows browser (with graphics acceleration turned on) against the Gateway at `localhost` (`docs/spike-report.md`). The measures it records, with their labels and limits, are in [docs/platform-checks.md](platform-checks.md), section "Story 7".

## Message contract

Every message between the browser and the Gateway is `{v, type, id, body}` under the model event `mapstudio.message`; errors are `{code, message}`. The types this version knows are listed in `common/.../Messages.java` and `web/typescript/messages.ts`: `point.click`, `point.click.reply` and `error` (contract 0.1.0; from 0.2.0 an `error` may also carry `batchId`, `op` and `conflicts`), from contract 0.2.0 `map.load`, `map.load.reply`, `edits.apply`, `edits.apply.reply`, `map.changed`, `tags.browse`, `tags.browse.reply`, `tags.resolve` and `tags.resolve.reply`, and from contract 0.3.0 (unreleased) `values.batch`, `popup.open` and `popup.close`. Their bodies, the error codes and the scripting API are in [docs/contract.md](contract.md).
