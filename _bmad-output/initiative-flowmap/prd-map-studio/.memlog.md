- (decision) PRD started from the final brief (brief-flowmap) and its addendum; brief decisions are the baseline.
- (decision) Working mode: coaching path, chosen by the user before activation.
- (decision) Stakes carried from the brief: solo, two days a week, reputation goal, template-first, open-source later; calibrates the PRD to a lean solo document.
- (decision) No inputs beyond the brief and addendum.
- (decision) Concerns confirmed: public props and events contract with a breaking-change rule; edit permission split between module and page; alarm presentation review (ER-27); WCAG 2.2 accessibility; Ignition 8.3 full Gateways only with live-verified SDK claims; web form factor, desktop editing and 390 px phone point moves.
- (decision) Entry point: journey-led (user asked for a suggestion); the 30-minute field build is the hardest criterion and is a journey.
- (decision) Admin and integrator grouped as one role for common tasks (create a map for a new field, create a map for an existing field with no map UI, modify an existing map); integrator additionally mass-provisions by CSV.
- (decision) CSV import needs a template: the tool shows or exports the CSV template a user must fill, per kind.
- (decision) Entry state for building a field: the map page, empty or nearly empty. No required order of work.
- (decision) Adding an item: a form or wizard for name and properties; location typed as lat and lon or picked on the map, like setting a point in Google Maps directions.
- (decision) Correctness of a built field is judged by people (operators and other users reviewing), possibly against an overlay of another map; overlay feasibility open.
- (decision) Failure cases for UJ-1 not known to the user yet; to be elicited.
- (assumption) Conflict with brief: user says operators or field admins update properties on a phone; brief limits phones to moving points. To confirm before applying.
- (decision) Phones: move a point and edit an item's properties (option b). Overrides the brief's move-only rule; brief updated to match.
- (decision) Map items link to existing assets in the host system, so the map can later show their state.
- (decision) Reference for checking a layout: satellite imagery as a basemap, or an imported reference layer.
- (decision) Idea from user: import CSV, KML or GeoJSON, then the user selects features and maps each to an existing asset.
- (decision) Location entry: show country, province or state, and city for typed coordinates as a sanity check; a zoom-to-location action in the form.
- (decision) Snapping: visible UI difference between a snapped and a floating line end; an unconnected pipeline is not critical.
- (decision) Duplicate names: allowed when the underlying assets differ; shown with a red underline and a tooltip, not blocked.
- (decision) Losing work when leaving halfway through a big layout must be prevented: a must-have.
- (assumption) Reframing from user, pending confirmation: Map Studio is the project's map view with role-gated admin tools, not a standalone editor. Viewers and operators see the configured map with popups; admins and integrators also see the Map Studio tools.
- (assumption) Popups, pending confirmation: a standard section (comms, site details, metadata) plus 3 or 4 configurable KPIs, each bound to an asset or tag path chosen in Map Studio, with a tag browser.
- (assumption) Storage, pending confirmation: user leans to the module persisting map data and work in progress (a database, cache or globals), which reverses the brief's 'module stores nothing'.
- (assumption) Assets come from the host project; the module must state what it requires and where the list comes from (CSV, a defined data model, or the module building the relationship).
- (assumption) No formal draft and release: work saves as it goes; sharing is by navigation or URL; viewing a work in progress is useful.
- (assumption) Reverse geocoding should be approximate and ideally offline, without a database.
- (decision) Confirmed: Map Studio is the project's map view with role-gated Map Studio tools; viewing and popups are first-version scope.
- (decision) Data binding is a major benefit: each map icon shows a comms status glyph and one critical KPI (for example pressure); crossing a set point changes the icon or colour. Threshold design to be worked out.
- (decision) Popup: metadata, comms, KPIs, and an optional navigation button to a page or URL that supports expressions or indirect values (for example the clicked CTB's own page). All popup parts optional.
- (decision) Source of truth: the Map Studio database owns the map; the template's git registry no longer owns map data. The project as a whole stays version controlled.
- (decision) First version stays a three-month target.
- (decision) Storage: the module saves to a database connection the project picks, creates its own tables, and saves as you go; no globals. Assets come from the project through a published contract. Reverse geocoding offline from bundled boundary and city data. No draft and release split.
- (assumption) State colours and icons driven by KPI set points are alarm presentation and need the template's engineering review (ER-27, docs/ux.md section 11).
- (decision) Set points: icon state comes from Ignition's own alarms on the tags (option a), not from limits set in Map Studio.
- (decision) Icon and popup setup is per kind of item with per-item overrides; tag paths relative to the item's base path.
- (decision) Popup links use placeholders filled from the clicked item (for example /ctb/{asset.id}); no full expressions.
- (decision) Alarms: each item maps an alarms path in the tag hierarchy; the icon can show an alarm count (optional) and the popup an alarm summary table (optional).
- (assumption) Unverified: alarm aggregate properties exist on folders and UDT instances at every level of the tag hierarchy in 8.3 (to check on a live Gateway).
- (assumption) A popup alarm summary is an alarm display; the template treats the Perspective Alarm Status Table as the authoritative alarm display and alarm presentation changes as engineering review items.
- (decision) Popup alarm summary embeds the built-in Perspective Alarm Status Table filtered to the item's alarms path (option a).
- (decision) Acknowledging alarms from the popup's built-in table is allowed, as the table already supports.
- (decision) User asked for UJ-2 to UJ-5 to be drafted for review.
